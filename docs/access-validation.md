## Repeating database/browser checks

Use a dedicated disposable PostgreSQL server, never a hospital database. The login must be allowed to create/drop test databases. Build both apps first. Set `DATABASE_URL` to an existing local database whose name ends in `_test`, `JWT_SECRET` to a synthetic test secret, and `PLAYWRIGHT_MODULE_PATH` to an installed Playwright module path or file URL. Its matching Chromium browser must be installed. From backend:

```powershell
node test/run-access-regression.mjs
```

The runner creates a separate database per suite, drops it on success and retains it on failure for diagnostics. The PDF test consumes the document generated by the doctor integration test. Without `PLAYWRIGHT_MODULE_PATH`, the catalogue browser subtest is skipped; the standalone browser scripts have a checkout-specific fallback path that must be changed/configured elsewhere.

`multi-role-docker-smoke.mjs` uses only the fixed isolated port 55446 and bootstraps a fresh synthetic installation. Do not forward that port to an existing LIS. Run it only against a separately created, empty test stack built from these Dockerfiles. It intentionally will not bootstrap an already initialized database. Isolated-stack configuration used no existing LIS volumes, loopback-only frontend access, a dedicated PostgreSQL service and synthetic secrets.

PDF generation/checks are `node test/render-access-guide.mjs` and `node test/check-access-guide.mjs`. Browser/PDF screenshots are generated in ignored `backend/test-results/`.

## What this does not prove or deploy

The existing running LIS services were left untouched. Apply the source upgrade after backup using the procedure in `another-machine-setup.md`. Builds/synthetic tests are not proof of real hospital rollout, load capacity, backup recovery, network access from another PC, HTTPS/VPN configuration, security certification or clinical acceptance.

The commercial license/activation service, source-free installer, registry release publication, automatic updates, arbitrary action-permission editor and mandatory second-person authorization are not implemented. Existing IT delegation remains; combining Technician and Report authorizer explicitly permits same-person authorization. The app has no independent patient-master deletion API or permanent-purge feature.
